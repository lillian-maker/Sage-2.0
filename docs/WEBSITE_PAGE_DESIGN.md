## 5. 企业服务：标准产品为基础，定制服务深入业务

### 5.1 定位与研究结论

企业服务不是企业版套餐介绍，也不是“全部从零定制”。对外明确两种供给：**标准化Sage产品**承载既有经营场景、数字员工协作与产品体验；**定制化服务**针对企业的数据、知识、业务流程及系统需求做评估和专项交付。订阅、实施、资源消耗、持续维护分别约定，不能一个“联系销售”按钮掩盖范围。

Qoder企业页的有效参考是“业务价值 → 具体能力 → 治理与衡量 → 下一步”的叙事顺序；其知识引擎、研发度量与认证属于Qoder自身，不迁移成Sage能力声明。结合原始组织设计，Sage的差异应落在经营对象、岗位责任、证据、授权及交付回执，而不是“更强模型”或“一个超级助手”。

页面语言用“可按需求评估、设计与交付”；正式对外使用“已支持/已交付”之前必须提供对应能力验证。这里的服务组合是建议供给结构，不代表团队已承诺全部工程、部署或合规能力。

### 5.4 四类定制服务：输入、工作、成果、验收逐项对应

锚点`#services`。标题：**把企业差异，变成可交付的能力**。四个服务编号形成宽横行，左4列为服务名与价值，右8列为具体内容；相邻行用极轻分隔。默认展开关键交付，不让客户连续点四个折叠才看懂。技术细节链接文档。

#### 01 数据采集与治理

对外文案：**让分散的数据，成为有来源、可核对的经营依据。**

- 适用问题：平台、店铺、投放、库存或服务数据分散；同一指标在不同报表中定义不同；更新滞后导致建议不可执行。
- 客户输入：合法可用的数据源、负责人、访问许可、字段说明、历史范围、更新频率及现有业务口径。不索要聊天中的密码或密钥。
- 服务工作：评估官方API、授权文件导入及已有数据库接入；识别品牌/店铺/SKU等主键；定义时区、币种、订单与退款口径；去重、增量同步、异常检测及权限撤销路径。第三方公开数据逐源评估条款与可用范围，不承诺绕过登录、反爬或平台限制。
- 交付物：数据源清单、字段与指标字典、映射规则、同步任务、质量与对账报告、异常处置说明。具体连接器需评估后列入合同。
- 验收方式：约定时间范围的源记录与目标记录核对；重复导入不重复累计；断点恢复；授权撤销后的停止访问；缺失和延迟能被识别。数量、频率与阈值在范围评估中确定，不虚构统一达标率。
- 边界：接通数据不等于数据完整；缺失不当作零；没有授权不采集。税务或监管解释需相应专业审核。

#### 02 企业知识与知识图谱

对外文案：**把商品、规则与经验，组织成能够引用的业务知识。**

- 适用问题：SKU、供应商、渠道、客户反馈与合规材料关系复杂；文件版本冲突；经验只掌握在个人手里；回答不能说明依据。
- 客户输入：产品资料、业务术语、规则与SOP、经审核的案例、知识所有者、适用范围及保密级别。
- 服务工作：先建立术语与来源规范，划分事实、规则、方法和案例；对文档设置版本、有效期与权限，设计检索评测。确有跨对象关系问题时，再建实体、关系、来源及时间模型，处理别名和实体消歧；不把所有文件都强行变成图谱。
- 交付物：业务词汇表、知识目录与更新责任表、检索与引用规则、评测题集；采用图谱时另交实体/关系模型、映射与冲突处理规则、权限及维护方案。
- 验收方式：已知问题能定位依据；旧版本不覆盖新生效规则；无权限对象不可检索；删除或撤权后不可继续被引用；无依据问题能指出不足；图关系能追溯到源记录。准确性与成本使用双方认可的测试集评估。
- 边界：表格指标优先结构化查询，文件问题优先普通检索，确有关系推理与跨域发现需求再评估图谱。知识图谱不是默认购买项，检索到内容也不授予行动权限。

#### 03 业务场景与数字员工定制

对外文案：**让数字员工按你的业务规则工作，而不只是换一段提示词。**

- 适用问题：已有经营场景与企业审批、品牌策略、市场限制或异常处理不一致；多个岗位交接后责任不清。
- 客户输入：经营目标、现行流程、角色与审批矩阵、判断规则、历史正反案例、例外与停止条件。
- 服务工作：映射任务输入、主责、协作与独立复核；定义阶段成果、验收条件、工具权限、预算和人工接管；版本化工作方法。增加岗位先评估职责是否真的独立，不按客户部门名无限生成员工。
- 交付物：场景说明与流程、岗位责任映射、阶段成果格式、审批与异常规则、测试用例、试点报告和操作手册。
- 验收方式：输入不足会停止或降级；成果交接能验证；高风险动作没有授权不得发生；异常可以接管；原始证据与执行回执可定位。使用正常、反例、权限拒绝、外部超时等用例，不只展示一次顺利演示。
- 边界：涉及投放预算、采购、商品发布、消息触达、退款及账号恢复，均需明确动作授权；“平台规则建议”不是法律或监管结论。

#### 04 业务产品与系统集成

对外文案：**把业务流程，落到团队真正使用的产品与系统里。**

- 适用问题：需要经营工作台、专属报告、审批界面、业务工具或与现有ERP/CRM/BI等系统连接；仅输出报告无法进入日常工作。
- 客户输入：使用人群、关键任务、现有系统接口与测试条件、权限约束、验收及运维负责人。
- 服务工作：复用标准Sage能力，设计必要界面、数据/API对接、审批和回执展示；按读写风险分阶段集成，先只读再受控写入；评估上线、兼容与升级策略。
- 交付物：需求与范围说明、页面/交互规格、约定的软件功能与接口、测试报告、部署与移交说明；源码、数据所有权及维护边界在合同中确定。
- 验收方式：真实任务端到端可完成；权限拒绝有效；重复调用不产生重复业务动作；失败和未知状态可追踪；升级与回滚路径有验证。效果以约定任务与业务结果复核，不以页面数量衡量。
- 边界：不默认提供私有化、单点登录、专属模型或全平台连接；不默认替换ERP等业务事实系统；不能为了一个客户长期复制并维护整套官网或产品分叉。

**持续服务单独约定**：数据更新与失败告警、知识维护、场景评测与版本变更、运行观察及问题响应，可在实施后单独评估。不把终身维护、固定SLA、无限需求和外部模型成本包含在“定制服务”四个字中。

标题：**定制从具体工作开始**。三行案例每行“问题 → 企业差异 → 交付 → 验收”，显著标“方案示例”。没有真实客户授权，不放客户Logo、收益数字或“已落地”。

| 问题 | 企业差异与定制重点 | 交付成果 | 如何判断完成 |
|---|---|---|---|
| 多品牌、多店铺的补货计划 | SKU映射、供应提前期、在途和现金约束、采购审批 | 有版本和约束说明的补货计划；获授权后的采购或履约回执 | 缺失提前期不擅自承诺；方案与库存对得上；没有授权不下单 |

### 5.6 怎样判断：直接使用、配置，还是定制

| 需求 | 建议路径 | 不需要重复建设的部分 |
|---|---|---|
| 现有场景已覆盖，只变品牌、市场与任务目标 | 标准产品与任务输入 | 不重造岗位框架、协作机制和页面 |
| 指标、资料、审批人或阈值不同 | 企业配置与知识/数据适配，评估是否需实施 | 不自动视为新增业务场景 |
| 阶段成果、审批、异常及系统连接不同 | 场景与集成定制 | 仍优先复用已有任务与授权边界 |
| 新使用人群、新业务工具或新的产品交互 | 产品专项定制 | 不默认另建全部基础能力或永久产品分叉 |

这张表放在服务说明之后，帮助用户缩小范围，而不是先让客户填写复杂技术清单。

### 5.7 交付过程与商业边界

标题：**从问题界定，到联合验收**。横向五步在手机转纵向，每步带明确成果，不使用没有依据的固定工期。

1. **需求评估**：确认问题、受益对象、数据与权限，形成范围/排除项与可行性判断。
2. **方案与报价**：确认标准订阅、专项实施、Sage Credits及第三方费用，列交付、验收、所有权和维护责任。
3. **受控试点**：用约定数据与测试集验证关键假设，先只读或人工审批；无价值/无权限时允许停止。
4. **实施与验收**：依据确认范围实现、测试和培训，交接异常处理、权限与回滚说明；签收不能替代实际用例验证。
5. **运行与迭代**：按另行约定范围跟踪数据、成果质量、使用与成本；新增范围走变更确认。

衡量建议：数据可用性、证据可追溯性、任务交付质量、人工返工、业务动作回执及成本。业务增长需基线和可比条件，不把活跃次数或模型调用量当ROI。

### 5.8 权限与数据：作为交付要求，不作为未经核验的认证声明

三列正文：“谁能看”核对组织/品牌/店铺/数据对象范围；“谁能做”核对动作、审批和服务身份；“出了问题怎么办”定义日志、接管、撤权和恢复。数据留存、删除、跨境传输及第三方处理范围按实际部署与合同核查，不泛称“数据绝不出境/完全合规”。

不放ISO/SOC2徽章，不声称已兼容企业SSO，不许诺24小时响应或7×24服务。以明确的实施检查项建立信任，不用别家资质替代Sage证明。

### 5.9 企业咨询与FAQ

锚点`#contact`。标题：**说说你希望先解决的经营问题**。说明：**告诉我们业务目标、现有系统和期望交付，再一起判断标准产品、企业配置或专项定制是否适合。**

建议表单：企业/品牌名称；工作邮箱或手机号；要解决的业务问题；需要的服务多选（标准产品、数据、知识、场景、产品/系统、尚不确定）。补充系统和资料可选，不强制客户理解技术架构。仅真实接收、隐私与校验具备后启用；当前未接通不得采集真实PII或模拟成功。保留`?path=product/fde`历史定位，fde映射定制服务章节而非新增套餐。

FAQ采用标题列表，核心答案默认可见：

- **一定要定制才能使用吗？** 不需要。先核对标准场景与可用范围；品牌、目标和资料差异不自动等于产品开发。

- **已有ERP、CRM或BI要替换吗？** 不默认替换。先评估只读取数、业务语义、审批及回执对接。
- **是否支持私有化或专属模型？** 当前不能作为默认已支持能力；需评估部署、成本、许可、维护及安全要求。
- **多久交付、多少钱？** 在明确数据源、场景、集成、验收及维护范围后报价；不编统一工期或参考价。

## 6. 文档：经营工作知识体系，而非介绍与FAQ堆叠

### 6.1 信息架构与阅读体验

文档首页标题：**把经营问题，变成可验证的工作**。摘要：**理解场景、准备数据、判断依据、确认授权。这里解释Sage如何组织工作，也说明何时需要补充信息、人工判断或企业实施。**

### 6.3 正文初稿一：定义一项可验收的经营任务

体裁：任务指南。适用：在委托分析或企业实施前界定工作；不是尚未开放的任务创建UI教程。

**先定义要做的决策，再定义要生成的报告。** “帮我提高销量”不能说明哪些数据适用，也无法判断任务是否完成。一个可验收任务至少包括：对象（品牌、市场、店铺、SKU或客户群）、决策（要判断或选择什么）、时间范围（使用哪个观察窗口）、约束（预算、库存、准入或动作权限）、成果（怎样检查交付）。这些是任务说明模板，不代表免费体验表单增加必填字段；免费入口仍为品牌名称或店铺链接。

例如：“检查指定Shopify店铺的公共首页和一个产品页，找出影响访客理解与购买准备的问题，输出有页面依据的优先行动清单；不访问后台、不修改店铺。”这可以验收页面观察和依据，但不能验收真实转化提升。后者需要经过授权的经营数据、可比基线及实验条件。

任务开始前应确认对象与数据是否一致。品牌名有同名对象时先确认；店铺不可访问时不能补造页面内容；缺少库存、提前期或币种等关键字段时，明确哪些判断无法形成。可以缩小任务做机会研究或页面检查，不能把缺失字段补成零后继续给确定结论。

验收时检查五点：成果是否回答原决策；依据是否在范围内且可定位；反证与待验证项是否保留；建议是否符合约束；如涉及外部动作，是否有真实授权和回执。报告写得长、岗位出场多或任务显示“完成”，都不能替代这五点。

### 6.4 正文初稿二：VOC机会研究——从声音到可验证命题

体裁：机制解释＋任务指南。VOC是消费者声音，属于新品机会证据研究，不是另增第十条经营流。

**先看声音来自哪里。** 公共评论、访谈、客服记录或调研反馈不是等价样本。记录来源、观察窗口、市场、品类、样本条件和合法使用范围，去除重复与无关内容；无法确认购买或使用背景时保留这一限制。不把“出现次数最多”直接解释为市场需求占比。

**将原话与判断分开。** 原始表达是证据；使用情境、问题分类和机会判断是分析。对每个机会保留代表性依据、适用人群、问题发生条件，以及不支持该判断的内容。需要引用时保持原意，不能为结论改写证据；涉及个人信息时只保留必要且经授权的内容。

**从机会转为假设。** 一个可验证命题说明目标用户、场景、当前痛点、预期改善、可能替代方案及验证方式。例如“某类用户在特定场景需要更方便的携带方式”是待验证命题，不是已经确认的新品销量。验证计划要有成功、失败和停止条件；规模、成本和阈值由任务范围决定，不使用通用“爆款分数”。

**交给下一岗位的不是一句灵感。** 交接包包括证据范围、主题与反证、机会命题、限制、建议验证及需确认的问题。后续产品定义、样品、供应、质量或准入岗位根据职责检验可行性。小样本不能证明市场份额；缺少样品与准入材料不能标记“已验证可上市”。

免费体验只用品牌名称启动公开资料范围内的研究，不能因此访问企业私有客服记录。免费资格与真实执行状态见账户规则，示例报告不代表已为输入品牌完成研究。

### 6.5 正文初稿三：Shopify——公开页面诊断与授权经营分析

体裁：规则参考＋机制解释。输入店铺链接不等于授权访问后台。

| 数据条件 | 可以检查 | 不能据此证明 |
|---|---|---|
| 合法可访问的首页与产品页 | 可见商品表达、导航、政策入口、公开购买路径与页面观察 | 真实订单、转化率、广告ROI、利润、库存准确性及客户留存 |
| 经合法授权并实际取得的经营数据 | 按范围核对订单/退款/商品/库存等事实，解释相应指标 | 未授权历史、受保护客户数据、其他店铺或平台的事实 |
| 已批准的具体写动作与工具权限 | 在批准对象、字段、时间和预算内执行；核验回执 | 对整店永久写入、自动营销触达、无审批扩大预算 |

Shopify官方API区分read与write scopes，部分数据还需额外权限。声明一个scope不代表已经取得商家批准，取得权限也不代表Sage已实现连接器。后台连接应经过正式授权流程，不要求用户在聊天中发密码或令牌。

公开诊断先确认店铺和市场，再记录观察时点与访问限制。密码保护、地域限制、反自动化或页面不可见时停止该部分，不绕过限制或用另一店铺推测。实际实现若只检查首页与一个产品页，就如实注明覆盖范围，不宣称全站扫描。

行动清单应包含问题位置、依据、影响假设、建议、优先级理由和验证方式。表达不清可以作为改进建议，不能据此断言收入损失金额。后续实验将变更前后窗口、活动、库存和其他影响因素分开，相关变化不直接宣称因果。

“已生成发布建议”“已批准发布”“平台已确认发布”是不同状态。没有平台回执时不能用报告完成标记代替店铺已更新；动作结果未知时先核验，不重复执行以碰运气。

### 6.6 正文初稿四：数据与知识，怎样成为可信上下文

体裁：机制解释。企业实施可据此编写数据与知识验收清单。

**先建立业务事实口径。** 同一SKU在渠道、ERP和仓库中的标识需要映射；收入、订单、退款、库存等指标需要观察范围、时间、币种和定义。查询结果应能回到源记录或已批准的汇总口径；时间窗口不同的两张表不能直接比较。数据延迟、缺失和冲突必须出现在结论限制中。

**不是所有资料都能当事实。** 产品规格与已核验记录可作为相应范围的依据；SOP是工作规则；分析框架是方法；历史案例提供参考但不证明当前任务；未经复核的模型输出是候选内容，不自动入库成为事实。每份知识至少说明来源、所有者、适用范围、版本或生效时间以及访问条件。

**先选择合适的检索方式。** 数值和聚合问题优先结构化查询；文档解释与定位可以先用普通检索；多商品、供应商、渠道或规则之间的关系问题才评估知识图谱。图谱建设需维护实体身份、关系、证据和时间，索引与更新也有成本；不是把所有文档接进向量库后就完成企业知识。

**用真实问题验收。** 选择常见问题、跨版本问题、相似对象问题、无依据问题和越权问题。分别检查是否找到正确来源、是否用错版本、能否说明冲突、是否拒绝无权限内容，以及回答不足时是否承认限制。不要只检验“能回答”；检索正确不代表回答一定正确，引用存在也不代表引用支持结论。

**维护和撤销同样重要。** 谁更新资料、谁审核生效、怎样作废、怎样处理已生成成果和索引缓存，都需约定。查询权限与执行权限分开；不允许“知道供应商合同内容”自动变成“可以发采购订单”。保留和删除政策依实际服务与法律核查，不编统一期限。

### 6.7 正文初稿五：数字员工怎样交接，何时需要人介入

体裁：机制解释＋规则参考。

**一项任务有结果负责人，不是所有岗位同时负责一切。** 负责人界定范围并组织成果，专业岗位完成各自工作，独立复核检验关键依据和约束。AI团队页面展示的是职责关系；头像、岗位配置和自然语言承诺都不授予真实业务权限。

**阶段交接应携带可检查的信息。** 在产品组织设计中，至少保留任务对象与版本、阶段成果、证据引用、限制与待确认项、下一阶段所需条件。接收岗位检查输入是否充分，而不是看到“完成”就继续。关键规则或数据发生变更时，旧结论的适用性需要重新核对。

**独立复核不是审批的替代品。** 复核可以判断证据、预算或规则是否满足；涉及外部动作仍由具备权限的人确认对象、范围、必要预算和停止条件。高风险动作要允许拒绝与接管，不将拒绝设计成阻碍用户前进的错误。

**三类异常，三种处理。** 输入不足：补充或缩小范围；规则冲突/无法通过复核：返工或人工裁决；外部动作结果未知：先查原交易、原动作或平台回执。未知不等于失败，不自动再次购买、发布或下单。

**完成分层判断。** 方案已交付、动作已授权、外部系统已接受、业务结果已复核不能混成一个绿色完成状态。任务关闭后的经验需要审核，不能把任意对话直接写入长期企业知识。完整生命周期及版本发布机制在技术参考中说明，不用七个状态按钮压过业务阅读。

### 6.9 正文初稿七：体验、席位与Sage Credits

体裁：规则参考。依据最新支付PRD写作，规则已确认不代表公网支付与任务已开通。

- **体验**：VOC品牌研究与Shopify店铺诊断二选一，仅一次成功免费体验，不绑定支付方式、不自动转付费。输入校验失败不消耗资格；任务锁定后中断恢复原任务，不因刷新新增资格。只有经服务端核实的不可恢复失败按确认规则释放。当前查看示例不代表执行过用户任务。
- **计费对象**：个人计划服务一个真人账户；企业方案2个真人席位起购。数字员工不是购买席位。Teams内含额度按席位独立，Enterprise席位不含Credits，资源单独购买；价格和额度以正式商品为准。
- **资源单位**：中英文统一Sage Credits，不称token、现金钱包或固定兑换货币。订阅内含按月发放，当期到期不结转；连续包年也按月发放，不一次发全年额度。
- **额外购买**：充值额度按确认收款起12个自然月有效，每笔保留独立批次。优先使用更早到期额度；同到期日先订阅后充值。额度不会因为取消订阅就自动退款；有效加购额度在订阅到期后的可用基础任务范围尚需正式公布。
- **预算与不足**：任务执行前确认预算，预留后结算与释放；不透支，超过批准预算先暂停确认。实际失败成本、跨期结算等未决策略不自行承诺全部返还。企业自动充值需单独授权、默认关闭并设月上限，不借订阅续费授权自动充值。
- **续费与取消**：连续包月/包年需明确授权。取消续费后保留已付周期权益；取消状态以服务端/渠道确认，不在点击时提前宣称成功。续费失败的补缴窗口不是免费延长服务。
- **月转年与升级**：月转年只允许同档或升级，立即从当天建立年度周期，月度剩余价值抵扣年费。月度升档支付新档完整月费，旧档剩余价值按天退款；年度升档补差，额度补差额且保留原周期。精确取整和未决额度结算须在商品/规则定稿后说明。
- **降档**：先取消订阅，当前周期结束后购买低档，不默认替用户安排降级。
- **退款与发票**：已开始月度订阅原则上不作普通退款；年度按规则退未开始完整服务月份，当前月不退；额外购买额度按可退未用比例与资格审核，不能一键承诺所有额度可退。错误扣款、法定例外按实际规则处理。发票由财务审核开具并发送至核验邮箱，不能展示尚不存在的自动开票能力。

金额、年价优惠、内含额度、失败计费、退款精度与其他未决事项仍以PRD和正式开放条件为准。本篇不替代结算前展示的有效商品、订阅协议或退款条款。

### 6.10 正文初稿八：企业实施准备与验收

体裁：任务指南。第一次沟通先提供业务问题、负责人、数据清单与期望成果，不直接发送原始客户数据和系统凭证。

准备清单包括：业务对象与时间范围；决策与成功/失败条件；源系统、字段、合法授权及访问环境；品牌/商品/指标口径；业务审批与可执行动作；试点样本及异常用例；交付所有权、运维负责人和维护范围。缺少关键授权或事实源时先做可行性评估，不直接承诺工期。

验收至少覆盖：数据对账与重复导入；正确/无依据/旧版本知识问答；跨租户、跨品牌和越权拒绝；正常阶段交接和输入不足；动作授权、重复调用、超时与回执；问题接管、撤权、回滚及移交。验收阈值和责任双方约定，不拿外部产品的性能指标当Sage承诺。

## 13. 注册、登录与账户菜单设计（待后续整体开发）

### 当前事实与新边界

当前 `backend/views.py::verify` 在未知身份验证成功后自动创建用户、个人计费账户及 owner 关系。新要求是“未注册用户先注册”，必须修改后端语义，不能只改前端标签。以下是待实施规格，不是已上线能力。视觉审阅见 `tmp/account-design-20261006/index.html`，无 API 调用、不收集真实资料。

### 页面与流程

官网未登录入口统一“登录”。点击进入独立登录页，保留安全 return 地址；表单底部“还没有账户？注册”进入同布局注册页。“已有账户？登录”可逆切换，保留已输入联系方式，不携带验证码、不在 URL 中保存联系方式。

登录页：标题“登录 Sage”，邮箱/手机号分段选择、联系方式、获取验证码、验证码、“登录”。仅验证现有身份，不隐式创建账户。发送验证码统一反馈，避免在发送前暴露某邮箱/手机号是否注册；证明身份之后若未注册，显示“该联系方式尚未注册”与“前往注册”，不自动创建。跳到注册可在内存中沿用已验证身份，但必须独立确认注册动作及有效期，不能复用已消费验证码绕过校验。

注册页：标题“创建 Sage 账户”，邮箱/手机号选择、联系方式、验证码，未预选的协议同意框、主按钮“创建账户”。无需填写公司或绑定付款方式；首次注册不自动订阅、不自动充值。注册成功建立个人账户，返回原页面；后台身份去重和并发事务沿用既有约束。若已注册，验证后引导“前往登录”，不创建重复账户。正式条款/隐私政策发布前不得开放注册。

验证码交互：发送中禁止重复点击；成功才进入服务端指定冷却；重新发送后清空旧验证码；校验失败就地提示，过期提供重新获取；到达次数/频率限制时明确稍后重试。所有倒计时以服务端规则为准，不在设计中编造秒数。服务不可用则禁用提交并提供重连，不显示假成功。页面保留键盘焦点、错误关联、自动填充与状态播报。

### 登录后的官网账户入口

以真实显示名或脱敏邮箱/手机号代替“登录”；无头像时用姓名首字符，不生成陌生头像。点击展开 288px 白色菜单，浅蓝当前项、轻边框与阴影；顶部显示名称、脱敏身份、当前个人/企业空间。桌面右对齐，手机使用不超出屏幕宽度的菜单。单击外部、Escape、完成导航后关闭；打开和关闭正确管理焦点。

菜单分组：① 个人设置（身份、安全及联系方式）；② 订阅与账单；③ Sage Credits（余额读取失败显示“暂不可用”，不显示0，加购只进入购买流程）；④ 组织与成员（有权限时显示管理入口）；⑤ 分隔后的退出登录。空间切换明确显示当前空间与权限，切换中清除旧账户数据，成功后更新所有入口；无权限不展示可执行操作。不存在的目的页面必须先实现，不允许菜单链接到空白页。

退出登录：服务端确认后入口恢复“登录”，清除当前账户视图与敏感表单；失败不假装已退出，展示重试与服务状态。会话过期清除账户数据并进入登录，保留允许的返回路径，不自动重放支付或修改类操作。

### 后续实施顺序与验收

1. 细化 `register/login` 意图及服务端验证契约，杜绝 login 创建用户；注册协议版本/同意记录、并发去重、安全 return 与审计事件。
2. 开发注册/登录独立状态、切换、验证码、限频/过期/错误恢复、同意校验及成功返回。
3. 全站复用现有导航身份逻辑，统一账号菜单、权限、空间切换、会话失效与退出状态；不新增无收益的管理器层。
4. 补齐个人设置/组织管理的真实目标页及未开放状态，然后连接账单、Credits。
5. 单元/接口测试：新身份登录不创建账户、明确注册才创建、重复/并发注册唯一、禁用账号、协议未同意不创建、验证码失效、限频、CSRF、return跨站拦截、双身份不能隐式合并、退出失败。
6. 桌面/手机/键盘验收所有状态，再接真实邮箱与短信发送渠道；真实服务就绪后才宣称注册登录整体完成。

待确认且不自行补全：正式协议文本与版本；手机号支持地区及短信渠道；邮箱和手机号是否允许绑定同一账户及冲突处理；个人设置与组织管理的首期开放范围。设计默认每次仅验证一种方式，不在常规登录强制双重验证；高风险账户变更需重新验证，具体动作另行确认。
