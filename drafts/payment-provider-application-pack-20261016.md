## 6. Apple Pay 和 Google Pay：现在能做什么

### Apple Pay

官方提供自行配置及支付服务商代接路线：[接入概览](https://developer.apple.com/apple-pay/implementation/)。获准的平台/支付服务商可代注册商户网站；是否需要 Sage 自有开发者会员、证书及 Merchant ID，应以选定服务商方案确认，不能一律要求先付费。

自行配置网站时，需 Merchant ID、支付处理证书、商户域名验证和商户身份配置：[网站配置说明](https://developer.apple.com/help/account/capabilities/configure-apple-pay-on-the-web/)。该配置不提供独立的资金收单/结算服务。

新申请公司开发者会员的要求包括法律实体、D-U-N-S、签约权限、公司域名邮箱及公开可用网站：[组织入会要求](https://developer.apple.com/help/account/membership/program-enrollment/)。不能把公司名称或 Apple Account 的存在当作满足全部条件。

| 现在可自主做 | 需要用户或外部条件 |
|---|---|
| 核对组织入会要求和两条路线；整理材料清单 | 公司准确主体资料、授权经办人、是否已有组织会员 |
| 准备询问收单机构是否代注册网站及续费适配 | 机构对本商户的具体答复 |
| 规划实际域名验证和证书用途，不执行生成/部署 | 选定路线、网站前置条件及明确操作授权 |

不在本次自行查个人账号、提交 D-U-N-S 企业数据、申请会员、付款或创建证书。若仍无公开完整公司网站，不把组织入会登记为就绪。

### Google Pay

可以先准备 Google Pay & Wallet Console 的 Merchant 业务资料及测试方案；创建资料与生产批准独立。[生产流程](https://developers.google.com/pay/api/web/guides/test-and-deploy/publish-your-integration?hl=en)要求受支持网关或符合 PCI DSS 的直接处理环境；网站申请需域名、集成类型及支付流程截图。

Sage 建议走 Gateway，不为钱包自行处理原始卡数据或扩大 PCI 范围。[开发准备](https://developers.google.com/pay/api/web/guides/setup?hl=en)要求 HTTPS 等条件；[周期付款文档](https://developers.google.com/pay/api/web/guides/resources/merchant-initiated-transactions?hl=en)不等于本主体、目标地区和所选网关已经获批。

## 13. Apple Pay / Google Pay 网站接入执行计划

> 执行者须先读本包和原支付 PRD，按 executing-plans 或 subagent-driven-development 逐项执行；本节只授权计划准备，不授权实名、接受条款、付款、创建凭据、部署或真实交易。后续实施不自动提交 Git。

**Goal：**为现有 Sage 网站接入经过主体/业务审批的钱包首次支付与月年续费，复用唯一订单和账本，不将钱包按钮当成收单许可。

**Architecture：**首期建议 Apple Pay 优先获准 PSP 代接、Google Pay 优先 Gateway；该建议尚不是渠道最终选型。由 Sage 或 PSP 中唯一一方调度续费，服务端核实收款后交付，未知结果查原单。自配 Apple 证书或 Google Direct 会增加维护/合规成本，只有确有必要且获批才改路线。

**Tech Stack：**既有 Django/PostgreSQL、`src/pages/billing.js` 及选定 PSP 官方钱包 SDK；本轮不安装 SDK、不新建 Provider/Adapter 层。

**Spec：**[支付 PRD R02/R03/R05](../../Sage/docs/Sage_支付PRD_2026-10-02.md)、本包第 5 节及[开发记录](../docs/BILLING_DEVELOPMENT.md)。

## 14. 四平台开发计划 · 2026-10-16

> **执行者必读：**本节是支付宝、微信支付、Apple Pay、Google Pay 的最新开发顺序，补充并覆盖第 10、13 节中“选定机构后才开始所有开发”的旧顺序；已有官方资料、历史执行结果和授权限制保留。使用 writing-plans 制定，后续按 executing-plans 逐项执行。所有开发任务目前均未执行，本次只追加计划；不自动 commit、push、部署、开户、创建凭据、接受协议、发送真实通知或交易。

**Goal：**在现有 Sage 官网和唯一 Django 账本上接入四种支付方式，先完成不依赖商户审批的开发，再分平台完成外部测试及获准真实首付、月年续费、取消、退款与对账。

**Architecture：**支付宝、微信是独立渠道；Apple Pay、Google Pay 是银行卡钱包入口，必须衔接实际收单机构，不能作为四套互不相干的账本。复用订单、支付尝试、授权及权益交付；先提交唯一派发占位，再发出请求；网络未知只查询原交易。钱包优先获准支付机构代接／Gateway，不采用 Google Direct 或自行解密卡数据绕开收单准入。

**Tech Stack：**既有 Django 5.2、PostgreSQL、原生网页 JS；支付宝优先官方 Python SDK；微信按官方 APIv3 协议选择适用接法，不为使用 Java/PHP SDK 新建服务；两个钱包使用官方网页 API 或最终选定支付机构的官方组件。不新增通用 Manager／Provider／Adapter／Registry 层。

**Spec：**[支付 PRD](../../Sage/docs/Sage_支付PRD_2026-10-02.md) R02–R05、R14–R18、R23–R27、R30、R35–R37；本包第 2、5、11、13 节；[开发记录](../docs/BILLING_DEVELOPMENT.md)最新商业门禁。本节扩大四种方式的开发准备范围，不代表四种都必须同日上线，也不取消 PRD 中独立 Visa/Mastercard 银行卡入口。

### 14.1 决策、范围和不等待原则

推荐顺序：**T1 共同安全链路 → T2 支付宝 → T3 Google Pay TEST → T4 Apple Pay → T5 微信支付 → T6 真实周期授权与续费 → T7 财务与回归 → T8 受控实款。** T0 商户资料／机构能力与各技术批次并行；某平台材料阻塞只暂停该平台的外部联调，不阻断其他可开发项。微信仍按原 PRD 后置，现阶段不为抢四路并行修改同一账务核心。

上述是开发投入优先级，不是强制四种首次支付全部完成才做续费。T6／T7／T8按渠道分别插入：支付宝条件先到位，就先完成支付宝闭环；不得等其他三家审批，也不得用未完成续费的单次付款代替连续订阅上线。

| 平台 | 开发路线建议 | 企业变更前可以做 | 外部联调前必须满足 | 暂不做 |
|---|---|---|---|---|
| 支付宝 | 直接接官方开放平台；PC 网站与手机外部浏览器按获准产品分别接 | SDK 封装为普通函数、金额转换、下单／查单／关单／退款及通知验证、本地反例；取得对应沙箱配置后调用沙箱 | 开放平台账号、对应沙箱应用与产品可用性、安全注入配置；生产另需正式应用和产品权限 | 不保证沙箱覆盖月年续扣；不把普通网站收款当周期扣款权限 |
| Google Pay | 先官方 TEST 付款面板；收款阶段用实际选定 Gateway 或其官方组件 | 设备可用判断、付款面板、取消／失败／未知交互、TEST 返回数据隔离 | TEST 面板需要可用浏览器／账号及 HTTPS 条件；网关联调另需准确 gateway 和测试商户参数 | 不将官方 example gateway 返回当处理机构扣款；不选 Direct |
| Apple Pay | 优先获准机构代注册网站并处理商户会话；必要时才评估自配 | 检查设备能力、金额／周期请求构造、取消与异常交互、服务端安全拒绝测试 | 代接机构配置，或自配 Merchant ID／证书／域名验证／测试账号及设备；域名实际可达 | 无配置时不承诺能调起有效付款会话；不为准备代码先购买开发者会员 |
| 微信支付 | PC 网站优先评估 Native 扫码；手机外部浏览器评估 H5，微信内网页评估 JSAPI | 下单／查单／关单／退款接口结构、签名和通知解密／验签的本地测试、前端扫码及失效状态 | 对应商户号、关联 AppID、商户 API 配置及场景产品权限 | 不默认拥有 APIv3 沙箱；不伪造可支付二维码；不将 JSAPI 当所有浏览器通用方案 |

“等变更后正式提交”是为减少资料不一致和重复核验的项目安排，不是各平台统一禁止提前开发／申请的规定。法人变更完成也不自动解除域名备案、正式商品／协议、商户审批和产品能力限制。此前用户所述预计两天只作资料协调窗口，不作为交付或审批时限承诺。

共同硬约束：深圳同一主体、CNY 整数分、月年真实续费、独立授权、明确失败不自动重扣、未知仅查询原交易。测试商品和资金与生产完全隔离；未批准的年价／权益／提醒规则不补默认值；生产不保存原始卡号、CVV 或钱包原始 token。测试凭据由有权人员安全注入，不读取用户 `.env` 或密钥文件，不进入聊天、代码或日志。

### 14.3 共用接口及信任边界（拟新增，不是已实现）

- `POST /api/billing/orders/{order_id}/pay`：登录／账户权限／CSRF有效后，以数据库中订单快照确定渠道与金额。客户端只发送当前订单允许的操作，不接受自定商户、金额、币种、到期时间或支付成功。支付失败／未知时不换幂等号重复调用。
- `GET /api/billing/orders/{order_id}`：沿用账户隔离订单查询作为浏览器恢复入口。渠道读请求可重复执行；浏览器状态、钱包回调和 URL 仅触发查询，不提供入账事实。
- `/api/payments/webhooks/alipay` 与 `/api/payments/webhooks/wechat`：按各自准确协议收原报文、验签、核商户与订单、持久化，再按平台约定响应。测试阶段默认拒绝；支付回调不是普通用户登录流程，但只允许此精确路径例外。
- Apple Pay／Google Pay 使用同一收单机构时，复用该机构唯一回调与查单处理，不再把钱包回调与银行卡回调分别入两笔账。机构未选定时，不预编造第三方路由、参数或验签格式。

- `PaymentFact` 当前唯一键是 `(channel, merchant_reference, transaction_reference)`。同一 PSP 交易在钱包与银行卡标签间的规范映射必须先测试；从已保存订单／派发记录推导渠道，不信任回调提供的任意 channel。不能用变换标签重复入账。
- 官网金额是整数分；支付宝的元字符串、钱包展示金额通过精确转换生成，不能用浮点计算。原始处理机构商户号映射到既有法律主体标识，不能把两者混用。
