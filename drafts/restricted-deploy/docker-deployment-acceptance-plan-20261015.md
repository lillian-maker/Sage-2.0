# Sage Docker 部署与验收 Implementation Plan

> **For agentic workers:** 使用 `executing-plans` 按本文件逐项执行；独立验证可使用 sub-agent。先读根 README、`docs/BILLING_DEVELOPMENT.md` 最新记录和本文件。用户已要求本地检查、部署准备、commit/push 和后续部署，但明确要求关键决策先沟通。待确认事项不能因沉默、计划入库或测试通过而视为批准。不创建 worktree。

**Goal:** 将确定版本的 Sage 通过独立 Docker 应用部署到 `ins-5ag0h225`，先证明本地可复建、运行隔离和可回退，再按批准的访问范围及功能逐项验收。

**Architecture:** 用户已批准新增独立 Compose 项目 `sage-preview`，包含 Nginx、Django/Gunicorn、PostgreSQL 三个长期运行容器；使用专属网络、数据卷、私有媒体及配置目录，初期仅映射宿主机回环 HTTPS 端口。另有复用应用镜像的受限一次性迁移任务，不长期运行。保留现有宿主机 Sage 和 PostgreSQL；不迁移、不共享旧数据。

**用户确认 · 2026-10-15：**首个验收目标为独立Docker受控部署，之后逐项接通认证、支付和业务场景；采用A三容器及新空库、保留旧Sage。上线对象明确为 **Sage-2.0深色首屏版本**，不是历史WorldPilot或Sage归档。授权当前本地适配、测试及GitHub提交；服务器安装、云端初始化和公网放行仍按具体批次确认。

**Tech Stack:** 现有 Python 3.12、Django 5.2、Gunicorn 23、PostgreSQL 16、Python 静态构建及 Playwright；TencentOS Server 4 官方支持的 Moby/Docker 与 Compose。版本及镜像须在适配时锁定，不使用浮动 `latest`。

**Spec:** 本次用户请求；原支付 PRD 与开发计划；`docs/BILLING_DEVELOPMENT.md`“各阶段详细执行顺序”；既有 `public-controlled-preview-plan-20261013.md`。本文件新增容器部署路径，不删除原七阶段商业上线目标。

## 2. 现有产品结构与实际缺口

- **官网：** `src/` 维护中英首页、AI团队、企业、文档、价格、下载、体验、账户等页面；`build.py`生成根页面和`dist/`。不手改生成文件，不使用旧dist发布。
- **账户：** Django负责邮箱/Google/手机链、账户组织、资料/私有头像、密码与会话、邀请码、注销、销售预约。代码/fixture通过不能替代真实供应商验收。
- **计费：** `backend/commerce/`已有商品、报价、订单、支付尝试/事实、订阅、Credits、企业席位等内部能力。销售、真实续费派发、加购仍关闭。
- **场景：** VOC/Shopify真实执行器与成本事件接入尚未完整验收；页面、体验资格、任务账务基础不能视为真实场景成功。
- **既有部署：** 主机Nginx→回环Gunicorn→Unix socket PostgreSQL，应用与迁移身份分离，私有媒体独立存储。容器化会改变网络来源和数据库认证，不能原样照搬配置。

本轮已定位的部署前工作：

1. 新增最小容器运行包装，现有依赖已包含Gunicorn，无需另造后端或新增业务抽象。
2. 受控预览关闭预约写入：仓库内Nginx草案反代全部API，而当前源码的匿名 `/api/consultations` 可创建记录；本轮没有对云端该接口执行POST。初期在预览Nginx准确拒绝该入口；若后续需要统一应用开关再单独决策。验收须证明拒绝且没有预约/审计写入。
3. 明确匿名会话：页面会请求 `/api/auth/session`并可能保存login_binding；浏览器验收不能宣称数据库零变化。
4. 保留production安全配置、精确Host、真实HTTPS、Secure Cookie/CSRF及精确代理信任。容器IP须从实际网络得到，禁止信任所有转发来源。
5. 私有头像在实际容器挂载上验证文件锁、原子写、失败恢复和多worker行为后才设置已验证标志；不直接通过Nginx公开媒体。
6. 实际OAuth前补齐Nginx错误日志可能泄露查询串的处置和验证；只删访问日志查询串不能算完成。
7. SMS部署检查默认依赖旧登录模板，真实新认证使用专用用途模板；短信启用前按用途修正检查并补反例。当前保持关闭。
8. 成本自动换Credits、成本齐全证明和跨月等分支仍须依最新产品规则接续；不为部署自行填写比例/权益/渠道。

## 4. 隔离部署设计（建议A）

```text
批准的浏览器来源（开放前先通过ICP/接入门禁）
        ↓ TLS443 + 来源限制 + 入口认证
Sage专属Nginx容器 → Django/Gunicorn容器 → Sage专属PostgreSQL16容器
        │                   │                       │
        只读dist/static     私有avatars持久卷        专属PG数据卷

首批只映射 127.0.0.1:9443 → Nginx HTTPS；不映射应用或DB端口。
原 /opt/sage、/etc/sage、sage_staging、8000/8443 和原systemd服务保留。
```

- 端口9443是根据本轮监听清单提出的候选，执行前重验；若已占用则停止并调整，不抢占原端口。
- 项目命名`-p sage-preview`；网络/卷/容器均由该项目创建，不使用无前缀external卷、不挂Docker socket、不用host网络或privileged。开工前若出现同名资源须先核实归属，不直接复用或删除。
- 专属bridge子网在实际主机路由/VPC及Docker网络盘点后选取无重叠网段；网关来源精确固定并配置到Gunicorn和`SAGE_TRUSTED_PROXY_IPS`，实际伪造头反例验收通过后才接认证。
- 网关单独加入edge bridge用于回环端口发布；web→app的frontend与app→db的backend保持internal，app/db不加入edge。Docker29最小实测中仅internal网络无实际端口映射，增加web专属edge后回环HTTP通过；最终还须通过完整HTTPS入口矩阵。
- web的app主机名通过extra_hosts绑定已固定且核验的SAGE_APP_IP，避免并行重启时服务别名尚未注册、外部DNS回落后被Nginx缓存。实际负例出现代理fake-IP/502，固定准确地址后的最小启动/重启对照200；不关闭TLS校验或扩大代理信任。
- DB网络不发布到宿主机。初始化/迁移凭据只给受限一次性任务，长期应用账号无DDL/superuser/CREATEDB/CREATEROLE权限。外部供应商尚未启用时不注入其凭据。
- 容器使用非root运行、只读代码/静态层、必要tmpfs和专属可写媒体/PG卷、`no-new-privileges`及最小capabilities。实际UID/卷权限须验证，不能只凭Compose字段声明隔离完成。
- 初始资源上限须在本地运行和云端空载基线后给出，再确定CPU/内存/PID及日志大小/保留数；不得从16核64GiB推定承载用户数。健康检查区分进程存活和DB就绪。
- 源码/镜像仅采用白名单构建输入；排除`.env`、密钥、证书、DB、媒体、日志、tmp、虚拟环境及Git历史。TLS/运行凭据运行时只读注入，不进入镜像层、仓库或构建日志。
- 仅新增必要Dockerfile、`.dockerignore`及现有部署目录内Compose/网关/数据库初始化配置；不新建Manager/Service等业务层。宿主机模板保留，避免把旧配置误用于新容器。
